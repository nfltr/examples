# Adding nfltr to your own .NET gRPC app

The fleet: a control plane and many .NET edge agents (often Windows,
behind NAT). Agents keep one gRPC session open to the control plane;
commands go down it, progress and results come up. Protobuf, generated
stubs, `Grpc.Net.Client`, ASP.NET Core gRPC.

This directory holds the app twice: `app/`, the app as written (the
control plane on a TLS port with a certificate from a private CA; agents
that trust that CA, check its name and keep the connection alive through
NATs), and `with-nfltr/`, the same app with the nfltr connect sidecar
added. The protocol (`proto/`) and the business logic (`common/`: the
agent's work, the session loop, the control plane's session registry and
dispatch) are shared and do not change. `migration.patch` is every
change; `migrate.sh <dir>` applies it to a copy of `app/` and checks the
result is `with-nfltr/`. `make dotnet-fleet` runs `app/`, applies the
patch, builds and runs the result, and checks that every command's
outcome, progress and output are the same in both.

Every number in this file and in README.md is written by
`test/report.py` from `migration.patch` and runs of that test.

- **No inbound port.** No fleet machine accepts a connection from the
  network; every sidecar connects out to the relay, agents behind NAT
  included.
- **Optional end-to-end encryption in organisation mode.** With `e2ee: true`
  a service's sessions are TLS 1.3 between the two sidecars that the relay
  cannot read, each side presenting the machine certificate its
  organisation issued (`nfltr org join`); the service serves only machines
  of the groups it lists (`allow_group`). The test checks that a machine
  outside the group is refused (exit 10) and a plain open of an encrypted
  service is refused (exit 4). The organisation's root stays with you
  (`nfltr org init`); the relay never holds a key.
- **Status and metrics per sidecar.** Each sidecar serves `/status`
  (sessions, failures and E2EE per mapping) and `/metrics`
  (Prometheus) on a local endpoint, the same for every app and language.
  For gRPC over plaintext HTTP/2 (as here, on loopback and unix sockets)
  `/status` also has hints: a client keepalive left over from the
  network, calls without deadlines, a channel per call, streams not read
  (https://nfltr.xyz/docs, the connect sidecar's "Hints").
- **What nfltr adds**: one more process per machine; a key of the account on every
  machine, its own (named as the machine); the relay on the path (latency against
  a direct TLS connection: README.md "Measured"; the hosted relay is not yours to run).

## The two shapes

```
(a) control plane -> agent, by name (with nfltr)

  ControlPlane ──gRPC──▶ 127.0.0.1:7001 ─┐                  ┌─▶ edge-1.edge-1/execute ─▶ Agent.Execute
  (Agent client)         (connect: edge-1)│  sidecar ══TLS══ relay ══TLS══ sidecar   (127.0.0.1:50051)
                  or     nfltr cat pipe edge-1.edge-1/execute ─┘   (E2EE: TLS 1.3 inside,       (agent: edge-1,
                                                    org certificates, relay sees records) connects out)

(b) agent -> control plane, one bidi session (app/ and with-nfltr/)

  Agent ──gRPC──▶ unix:/run/nfltr/fleet.sock ─▶ sidecar ══ relay ══ sidecar ─▶ Fleet.Session
  (Fleet client)  (Windows: pipe:nfltr-fleet)  (connect: fleet)        (agent: controlplane)  (127.0.0.1:5000)
                  Hello, Update ... ▲▼ Command, Cancel ...
```

`SidecarChannel.For` (`with-nfltr/shared/SidecarChannel.cs`) is a
`SocketsHttpHandler` whose `ConnectCallback` opens the named pipe or unix
socket, or `http://127.0.0.1:<port>` for a loopback endpoint.

the sidecar's local endpoint. Per control plane: its sidecar and file;
the Fleet listener on loopback.

## Organisation (end-to-end encryption)

With `e2ee: true` the session between two sidecars is TLS 1.3 that the
relay cannot read, between machine certificates your organisation issued
(docs: "Organisation enrolment"). Nothing comes from the relay:

1. Once, the owner makes the organisation and its groups and serves
   enrolments (on a machine you trust; the root key never leaves it):

   ```
   nfltr org init --root file --groups controlplane,edge --recovery-out recovery.key
   nfltr org serve
   ```

   `init` prints the root's and the recovery key's fingerprints
   (`sha256:...`); provisioning gives both to every machine.
2. Provisioning gives each machine a key of its own, its account machine
   named as its agent (`edge-1`; an organisation machine's name is its
   account machine's name), makes one single-use token per machine of that
   name, and redeems it on that machine, token on stdin:

   ```
   nfltr org token --name edge-1 --group edge \
     | nfltr org join --root <root fingerprint> --recovery <recovery fingerprint> --token-file -
   ```

   The machine's certificate and key stay in its nfltr config dir
   (`NFLTR_CONFIG`; 0600), renewed by the sidecar while it runs.
3. Each `e2ee: true` service lists the groups that may open it
   (`allow_group`): the agents' `execute` the group `controlplane`, the
   control plane's `fleet` the group `edge`. A machine outside them is
   refused at the handshake (`nfltr cat pipe` exit 10); `nfltr org revoke`
   cuts a machine off.

A plain open of an `e2ee: true` service is refused (exit 4), and an
enrolled machine opens a service that is not in organisation mode only
with `plain: true` / `--plain` (else exit 7). Nothing is downgraded.

## Who runs the sidecar

- **Beside the agent** (a systemd unit or Windows service, or a container
  in the agent's network namespace): the service manager restarts it; the
  agent keeps its session loop and retries while the sidecar is away.
- **Owned by the agent** (`Agent --Sidecar edge-1.yaml`): the agent starts
  `nfltr up -c <file> --exit-with-parent --log-format json`, logs both, and
  stops when the sidecar exits (the service manager then restarts both).
  On Windows the child goes into a Job Object with
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (`with-nfltr/shared/Job.cs`, `with-nfltr/agent/OwnedSidecar.cs`), so it dies with
  the agent however the agent ends. On Linux start it from a thread that
  lives as long as the process (the main thread): the parent-death signal
  follows the thread that started the child.

## Rollout for a fleet

Both paths run side by side on every agent; config picks one; config
undoes it. `migration.patch` is the end state; during the rollout the
builds carry both sides of it.

1. Install the sidecar on a few agents with the file above. The control
   plane's sidecar publishes `fleet` on a loopback listener next to the
   TLS one: the same `Fleet` service, two entries under
   `Kestrel:Endpoints`.
2. Ship an agent build that keeps `ControlPlaneChannel.cs` beside
   `SidecarChannel.cs` and picks one by config (a `ControlPlane:Url`, or a
   sidecar endpoint), then switch an agent's session by config. The
   control plane's session registry
   shows which agents arrived through which listener; the sidecar's
   `/status` and `/metrics` show sessions, failures and E2EE per mapping.
3. For (a), the control plane's inventory gains a per-agent route
   (`mapping` or `dial`).
4. Roll back an agent by setting its previous value; nothing else changes.
5. When every agent is on the sidecar, close the TLS listener and ship
   the builds of `with-nfltr/` (the patch applied).

`e2ee` is per service: an agent can join with `e2ee: false` (and a mapping
with `plain: true`) and switch on later; `edge-3` in this example is such an
agent. `/status` says `"e2ee": false` for its sessions.

## What the patch removes, what stays

Removed by the patch (measured above): the TLS listener, the private CA
and the certificate it issues, the client's TLS trust and server-name
code, and the HTTP/2 keepalive on both sides (the network hop is the
sidecar's: its relay link has its own liveness, and a session it loses is
closed on the local socket, which the application sees as UNAVAILABLE).

Stays in the application (`common/`, unchanged by the patch): gRPC
deadlines, cancellation, the session's reconnect loop with backoff, retries
on UNAVAILABLE (the sidecar fails a call at once rather than queueing it),
and the application's own authorization.

New to operate: one sidecar process beside each app (or owned by it), and
a key file of its own on each machine (see Limits).

## Limits

- One name is one agent. `edge-1.edge-1/execute` (agent `edge-1` on
  machine `edge-1`: `<machine>.<agent>/<service>`) reaches exactly one sidecar;
  there is no spreading of calls over several agents behind one name yet.
  A control plane picks the agent (that is what this fleet wants); a
  load-balanced service would need a balancer behind one agent.
- The relay authenticates the machine's certificate, not the agent. A
  machine of the account reaches every service of the account, and a session's Hello
  names an agent the control plane cannot verify from nfltr alone (no
  caller identity on the wire yet). Keep the application's own per-agent
  credential (for example a token in gRPC metadata) and check it.
- A machine certificate lives a day and the sidecar renews it while it
  runs; a machine off for longer joins again with a new token.
- A static file holds one mapping per agent. A large or changing fleet
  calls agents through `nfltr cat pipe` (one child process per connection;
  `with-nfltr/shared/DialChannel.cs`; `--plain` for an agent not on E2EE yet).
- Windows: the named pipe, Job Object and parent-death code compile, but
  this example's end-to-end test runs only the Linux side, in containers.
- Needs nfltr with the connect sidecar (`nfltr up` with `connect:`) and a
  relay that supports it (the hosted relay or a current `nfltr-relay`).
